# Queue Certification

Generated by the VeloCity Workstream Reliability Framework (WRF) — Phase 7.

## Queue Architecture

VeloCity uses a Postgres-native queue (`automation_queue` table) as the primary job queue. Redis is used as a secondary cache layer for high-frequency operations.

## Certification Criteria

A queue is certified as healthy when all of the following are true:

1. **Depth within bounds** — fewer than 100 items in `pending` state
2. **No stuck items** — no items in `pending` state with `created_at < NOW() - INTERVAL '10 minutes'`
3. **Failure rate acceptable** — worker failure rate below 5% (see WORKER_HEALTH_REPORT.md)

## Queue Health Data Shape

```typescript
interface QueueHealthEntry {
  depth: number;          // total pending items
  stuckItems: number;     // pending > 10 minutes old
  health: WorkstreamHealth;
}
```

## Health Thresholds

| Metric | Healthy | Degraded | Offline |
|--------|---------|----------|---------|
| Depth | < 100 | 100–500 | > 500 |
| Stuck items | 0 | 1–50 | > 50 |

Overall queue health = worst of both metrics.

## Queue Schema

```sql
CREATE TABLE automation_queue (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL,
  event_type TEXT NOT NULL,
  payload JSONB NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  processed_at TIMESTAMPTZ,
  retry_count INTEGER NOT NULL DEFAULT 0,
  CONSTRAINT automation_queue_status_check
    CHECK (status IN ('pending', 'processing', 'completed', 'failed', 'permanently_failed'))
);

CREATE INDEX idx_automation_queue_pending ON automation_queue (tenant_id, created_at)
  WHERE status = 'pending';
```

## Queue Operations

### Enqueue
```sql
INSERT INTO automation_queue (tenant_id, event_type, payload)
VALUES ($1, $2, $3);
```

### Claim (worker-side, SKIP LOCKED prevents double processing)
```sql
SELECT * FROM automation_queue
WHERE status = 'pending' AND tenant_id = $1
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

### Complete
```sql
UPDATE automation_queue
SET status = 'completed', processed_at = NOW()
WHERE id = $1;
```

## Stuck Item Resolution

Items stuck in `pending` for > 10 minutes indicate a worker crash mid-processing or a network partition. To resolve:

1. Identify stuck items:
   ```sql
   SELECT * FROM automation_queue
   WHERE status = 'pending'
     AND created_at < NOW() - INTERVAL '10 minutes'
   ORDER BY created_at;
   ```

2. Reset to pending if the worker is recovered:
   ```sql
   UPDATE automation_queue SET status = 'pending' WHERE id = $1;
   ```

3. Mark as failed if the event cannot be replayed:
   ```sql
   UPDATE automation_queue SET status = 'permanently_failed' WHERE id = $1;
   ```

## Accessing Queue Health

**Dashboard:** Queue depth and stuck items are shown in the "Queue Status" panel on `/admin/runtime/workstreams`.

**API:** The `queues` field on `PlatformHealthReport` from `GET /api/admin/runtime/workstreams`.

## Redis Queue Layer

For high-frequency operations (< 100ms SLA), Redis is used as a secondary queue via BullMQ-compatible patterns. When Redis is unavailable, operations fall back to the Postgres queue with degraded latency. This degraded mode is indicated in the workstream health matrix.
