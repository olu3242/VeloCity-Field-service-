## What changed this batch

An initial pass found and closed two real cross-tenant exposure paths, both missed by the prior `SECURITY_MULTITENANCY_CERTIFICATION.md` audit because that audit checked table-level RLS policies but did not separately re-verify every route that deliberately uses the RLS-bypassing service-role client:

1. `/api/runtime/trace/[id]` — now tenant-scoped (see `AGENT_LOG_SECURITY_CERTIFICATION.md`).
2. `src/app/dashboard/page.tsx`'s commercial-account lookup — now uses the authenticated client, relying on the existing correct RLS policy instead of a manual (and previously absent) tenant check.

A second, deeper re-audit pass — grepping *every* `getAdminClient()`/`createAdminClient()` call site across `src/app/**` and `src/lib/**` rather than spot-checking — found four more real cross-tenant gaps, all now fixed:

3. **`src/app/admin/lax/page.tsx`** (LAX Command Center architecture-health page) — all ~10 parallel queries (`automation_queue`, `automation_runs`, `agent_logs`, `jobs`, `providers`, `disputes`) used the service-role client with no tenant filter, so any admin viewing this page saw every tenant's queue/job/dispute/agent-activity data mixed together. Fixed: the page now resolves the requesting admin's own `tenant_id` (redirecting to `/dashboard` if absent) and adds `.eq("tenant_id", tenantId)` to every query.
4. **`src/lib/governance/drift-detector.ts`** — `detectDrift()`, called by `/admin/lax`, ran its stuck-jobs (`jobs`), dead-letter (`automation_queue`), and recent-failures (`automation_queue`) checks with no tenant filter, so the drift score and drift items shown to one tenant's admin were actually computed from platform-wide data. Fixed: `detectDrift()` now takes a required `tenantId` parameter and filters all 3 queries by it; its caller passes the admin's own tenant.
5. **`/api/automation/status`** (dashboard stats API) — all 6 parallel queries (`automation_queue` ×3, `automation_runs`, `automation_events`, `payout_queue`) used the service-role client with no tenant filter. Fixed: resolves `tenantId` via `getTenantId(profile)` and filters the queue/run/event queries directly. `payout_queue` has no `tenant_id` column at all (confirmed by grepping every migration — never added after `002_automation_engine.sql` introduced the table), so it's instead scoped via a `jobs!inner(tenant_id)` join filtered on `jobs.tenant_id`, since every payout row belongs to exactly one job which does carry a tenant.
6. **`/api/admin/runtime`** (operator-action API) — three distinct gaps in one route: (a) `GET`'s queue-stats/recent-runs/recent-errors queries had no tenant filter; (b) `POST`'s `replay_event` action looked up the target event by id alone, with no tenant filter, meaning an admin could replay another tenant's event into the queue (and the re-queued row's `tenant_id` would fall back to `null` rather than any real tenant); (c) the operator-action audit-log insert never set `tenant_id` at all, so every pause/resume/disable/enable/reset/replay action was recorded in `audit_logs` under whatever default the column falls back to, not the acting admin's actual tenant — an audit-trail correctness defect on top of the read-isolation ones. Fixed: `assertAdmin()` now returns the admin's `tenant_id`; `GET` filters all 3 queries by it; `replay_event` filters its lookup by it and defaults the re-queued row's tenant to the admin's own; the audit-log insert now sets `tenant_id: tenantId` explicitly.

No other admin-client (service-role) call site in `src/app/**/page.tsx` or `src/app/api/**/route.ts` was found querying tenant-scoped data without either (a) an explicit `.eq("tenant_id", ...)` filter, or (b) being a route that is itself the tenant boundary (e.g. cron routes authenticated via `CRON_SECRET`, which operate platform-wide by design and are not user-tenant-scoped).

A third pass — this time tracing every `src/lib/**` intelligence/report module reachable from `/admin/command-center` rather than only `src/app/**` call sites — found six more real cross-tenant gaps, all now fixed:

7. **`src/lib/membership/membershipRevenueIntelligence.ts`**'s `computeRecurringRevenueIntelligence()` queried `membership_subscriptions`, `membership_events`, `membership_plans`, `membership_plan_pricing`, and `revenue_records` with no tenant filter at all — MRR/ARR/renewal/churn/plan-profitability figures shown on Command Center mixed every tenant's membership revenue together. Fixed: the function now takes a required `tenantId` and filters all 5 queries by it; its one caller (`/admin/command-center`) passes the admin's own tenant.
8. **`src/lib/membership/membershipRetentionIntelligence.ts`**'s `computeMembershipRetentionIntelligence()` — same gap, across `membership_subscriptions`, `membership_entitlements`, `membership_usage`, `jobs`, `disputes`, `reviews`. Fixed the same way; also fixed its other caller, `AliceAgent.assessMembershipRetention()` (invoked by the `membership_cancelled`/`renewal_failed` automation handler), which now threads the tenant id from the triggering event's payload.
9. **`src/lib/commercial/commercialRevenueIntelligence.ts`**'s `computeCommercialRevenueIntelligence()` — same gap, across `commercial_contracts` and `revenue_records`. Fixed the same way.
10. **`src/lib/governance/executiveIntelligence.ts`**'s `computeExecutiveIntelligence()` — aggregates the three reports above plus its own unscoped `market_opportunities` query. Fixed by threading `tenantId` through to all three delegated calls and adding the filter to its own query.
11. **`src/lib/membership/membershipCatalog.ts`**'s `listMembershipPlans()` — queried `membership_plans`/`membership_plan_pricing`/`membership_entitlements` with no tenant filter, so a customer's membership cross-sell/upsell recommendations (via `membershipGrowthIntelligence.ts` → `NovaAgent.recommendMembershipGrowth()`, triggered by the `membership_expiring` automation handler) could recommend another tenant's plans. Fixed: now takes a required `tenantId`, threaded from the triggering event's payload through `computeMembershipGrowthIntelligence()` and `recommendMembershipGrowth()`. Its sibling export `getMembershipPlanBySlug()` was found to have zero callers anywhere in the codebase — removed as dormant code per this batch's Phase 3 rule, rather than retrofitted.
12. **`src/lib/expansion/marketDemandIntelligence.ts`**'s `computeMarketDemand()` and **`src/lib/expansion/marketSupplyIntelligence.ts`**'s `computeMarketSupply()` already fetched the requesting territory's own `tenant_id` (to stamp it on their `market_demand`/`market_supply` upserts) but never used it to filter their own read queries (`jobs` by zip in the demand case; `service_areas` and `providers` in the supply case) — a real bug where the write side was correctly tenant-scoped but the read side wasn't, since zip codes are not guaranteed unique across tenants. Fixed: both now filter their read queries by the territory's own `tenant_id` too.

`src/lib/expansion/marketOpportunityIntelligence.ts`'s `computeMarketOpportunities()` was checked and needs no change — it delegates entirely to the two functions above (now fixed) and otherwise only reads/writes rows scoped by the territory's own id.

## Known deferred gap (governance singletons)

One tenant-boundary gap was found but **not** fixed in this batch, and is recorded here rather than silently left out: the in-memory `operator`/`circuitBreaker` governance singletons (`src/lib/governance/operator.ts`, `src/lib/governance/circuit-breaker.ts`) that back `/api/admin/runtime`'s `POST` actions are platform-wide state, not tenant-scoped. A tenant's admin calling `pause_runtime`, `resume_runtime`, `disable_agent`, `enable_agent`, `disable_event_type`, `enable_event_type`, or `reset_circuit` affects every tenant's automation, not just their own. This is a blast-radius/least-privilege issue between authenticated tenant admins — the endpoint is still correctly gated behind `assertAdmin()`, so it is not an unauthenticated or unauthorized-role exposure — but it is a real tenant-isolation gap in effect. Making the singletons tenant-aware requires a state-model change across both modules and every reader of `getOperatorState()`/`getAllCircuits()`, which this batch's "no new frameworks" constraint puts out of scope. It is tracked in `CERTIFICATION_REMEDIATION_PLAN.md` (finding #18) as a deferred HIGH finding and flagged as a hard prerequisite for Franchise OS, which will need genuinely tenant-aware operator/circuit state regardless.

**Status: CERTIFIED WITH ONE DOCUMENTED DEFERRAL ✅** — every business domain's tenant boundary is enforced either by RLS (for RLS-respecting clients) or by an explicit application-level tenant filter (for the routes/lib modules that deliberately use the service-role client); all twelve previously-undetected read/write isolation gaps found across all three audit passes are closed. The one remaining gap (governance-singleton blast radius) is an authenticated-admin-to-authenticated-admin issue, not a data-isolation breach, and is explicitly deferred with rationale above rather than left undocumented.
