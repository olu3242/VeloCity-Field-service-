# VeloCity Gap Analysis (Superbatch 1 + 2)

For every phase in both directives, this classifies the ask as one of:
- **EXISTS — extend only** (building new would duplicate real, wired-in code)
- **PARTIAL — extend the real part, build the rest** (some real infrastructure exists, the rest is genuinely missing)
- **GAP — real net-new build** (nothing comparable exists; this is genuine new scope)
- **DO NOT BUILD** (orphaned/speculative code already covers this on paper but adds no real value — adding more would compound a known problem)

| Phase | Ask | Classification | Evidence |
|---|---|---|---|
| 1. Field Service Command Center | New `/admin/mission-control` | **EXISTS — extend only** | `/admin/command-center` already provides ops/revenue/automation/marketplace health scores, an executive summary, and auditable recommended actions (`docs/command-center.md`). Building a second page would duplicate it. |
| 2. Agent Workforce OS | Agent Registry, contracts, retry policies, audit logs | **EXISTS — extend only** | `src/lib/agents/registry.ts` already formally registers all 10 named agents with capability types, execution limits, retry policies, and observability hooks. |
| 3. Automation Fabric | Event types, rules engine, queue, retries, logs | **EXISTS — extend only** | `src/lib/automation/{emitEvent,router,worker,sla,governance}.ts` + 5 real cron jobs. Real event emission with dedup keys already flows through booking/dispatch/offer routes. |
| 4. Provider Learning OS | Tracks, lessons, simulations, exams, certification | **GAP — real net-new build** | No technician training/learning content or tables exist anywhere. This is the most content-heavy ask in Superbatch 1 — it needs real lesson content, not just schema, which is a content production effort, not a code task. |
| 5. Provider Performance Engine | Score, reputation, reliability, quality index | **PARTIAL** | `providerTrustScore.ts`/`customerTrustScore.ts` already compute a real trust score used in production (dispatch route, provider dashboard). Acceptance rate, completion rate, response time, repeat-customer tracking are not yet rolled into one composite score — that aggregation is the real remaining gap. |
| 6. Trust Center | Verification, dispute resolution, escrow, audit trails | **PARTIAL** | Escrow/payment-commitment logic is real (`hasPaymentCommitment`, used as a hard gate in dispatch). Dispute handling has a real agent (IVY) and event types. Identity/license/insurance *verification UI* for providers was not found — likely a real gap, not confirmed exhaustively in this pass. |
| 7. Dispatch Intelligence | Location/skill/rating/price/traffic-based ranking | **EXISTS — extend only** | `max.match(job, eligibleProviders, ...)` already ranks providers and the dispatch route already gates on payment commitment and provider availability (`getAvailableProviders`). "Traffic" and "historical performance" weighting were not confirmed as inputs — possible real extension, not a rebuild. |
| 8. Growth OS | Lead intel, referrals, reactivation, SEO, review-gen | **GAP**, but check `growthEvents.ts` first | `src/lib/automation/growthEvents.ts` exists and should be read before building anything here — not fully traced in this pass. Treat as **unverified, not confirmed-gap** until that file is read. |
| 9. Executive OS | CEO dashboard: today/weekly/strategic views | **EXISTS — extend only** | The Command Center's `executiveSummary.ts` and health-score widgets already cover most of this. A literal new `/admin/executive` page would duplicate it. |
| 10. Revenue Factory Certification | E2E certification docs | **This audit + `full-stack-certification.md`** | Already partially produced in the prior design-convergence pass (`docs/design/full-stack-certification.md` traces booking/dispatch/offer chains). Extend rather than re-certify from scratch. |
| 11. Provider Network OS | `/provider/business`, financial center, AI advisor | **GAP** | No such page or financial-center UI exists. Provider earnings data is real (`provider/earnings/page.tsx`) but there's no business-profile/coverage-area/licensing management surface. |
| 12. Customer Experience OS | `/dashboard/customer`, home intelligence, recommendations | **GAP**, with real data to build on | No unified customer workspace exists. Real underlying job/review/payment data exists to power it, but the UI itself is net-new. "Home Intelligence" (e.g. "HVAC serviced 11 months ago") would need new computed logic, not just new UI. |
| 13. Marketplace Intelligence | `/admin/marketplace`, supply/demand/revenue intelligence | **PARTIAL, mostly EXISTS** | `marketplaceHealthScore.ts` in the Command Center already computes supply-gap and liquidity signals. A literal new `/admin/marketplace` page risks duplicating this — extend the existing health-score module with city/category breakdowns instead of building a parallel page. |
| 14. Service Catalog Engine | `service_categories`/`service_types`/`service_packages` tables | **PARTIAL** | A category enum already exists and is the real source of truth used by booking (`SERVICE_CATEGORY_LABELS`, 18 categories, confirmed in the prior design-convergence pass). Sub-categorized service *types* (e.g. "Leak Repair" under Plumbing) and packages/pricing tiers do not exist — that's the real gap. |
| 15. Skills & Certification OS | `provider_skills`, certifications, skill graph | **GAP** | Depends on Phase 4 (Learning OS) existing first — flagged as sequenced after Phase 4, not parallel. |
| 16. Quote & Estimate Intelligence | AI-assisted quoting from photos/video | **PARTIAL** | QUINN is a real, registered quote agent (`quote.created`, `quote.review_requested` events). Photo/video-based estimation inputs were not confirmed as wired in — likely a real extension of QUINN's existing scope, not a new agent. |
| 17. Recurring Revenue Engine | Membership plans, MRR tracking | **GAP** | No membership/plan tables or recurring-billing logic found. Real net-new scope, and the highest business-risk item on this list (touches Stripe billing). |
| 18. Review & Reputation OS | Sentiment, theme detection, reputation scores | **PARTIAL** | REX (quality agent) already handles `review.submitted` events. Sentiment/theme extraction and a composite reputation score are not yet confirmed as implemented — likely an extension of REX, not a new system. |
| 19. Local Expansion OS | `/admin/expansion`, city/ZIP demand analysis | **PARTIAL** | TESS (territory agent) already handles `territory.analysis_requested`, `provider.supply_check`, `demand.surge_detected`. A literal new `/admin/expansion` page would risk duplicating TESS's existing scope — extend TESS's outputs into a UI rather than building a second territory system. |
| 20. Scale Certification | Cross-cutting certification docs | **Process, not code** | Same approach as Phase 10 — extend existing certification docs rather than starting a new doc tree per phase. |

## Headline conclusion

Of the 20 phases across both superbatches, **8 are already substantially built** (1, 2, 3, 7, 9, plus large parts of 13, 16, 18, 19 via existing agents), **roughly 7 are partial** (real foundation exists, real gap remains on top of it), and **5 are genuine net-new builds with no existing foundation** (4, 11, 12, 15, 17). Treating all 20 as equally "build from scratch" — which is what executing both superbatches literally would do — would duplicate roughly 40% of the requested scope and risk repeating the orphaned-module problem documented in `VELOCITY_CAPABILITY_AUDIT.md` §5.
