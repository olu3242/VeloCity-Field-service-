# Worker Health Report

Generated by the VeloCity Workstream Reliability Framework (WRF) — Phase 7.

## Overview

Worker health tracks the execution state of background automation workers. Workers process items from the `automation_queue` table and log their runs to `automation_runs`.

## Health Metrics

The health aggregator (`src/lib/workstream/health-aggregator.ts`) collects the following worker metrics on every health check:

| Metric | Source Table | Window |
|--------|-------------|--------|
| `totalRuns` | `automation_runs` | Last 30 minutes |
| `failedRuns` | `automation_runs WHERE status = 'failed'` | Last 30 minutes |
| `failureRate` | `failedRuns / totalRuns` | Derived |
| `health` | Based on failure rate | Derived |

## Worker Health Thresholds

| Failure Rate | Health Status |
|-------------|--------------|
| 0–5% | `healthy` |
| 5–20% | `degraded` |
| > 20% | `offline` |

## Worker Data Shape

```typescript
interface WorkerHealthEntry {
  totalRuns: number;
  failedRuns: number;
  failureRate: number;     // 0.0 – 1.0
  health: WorkstreamHealth;
}
```

## Automation Architecture

Workers are implemented as Supabase Edge Functions triggered by:
1. `pg_cron` scheduled jobs (every minute, every 5 minutes, etc.)
2. Direct invocation from API routes on specific events (e.g., `booking_created`)

Each worker:
1. Claims a batch of items from `automation_queue` using `SELECT ... FOR UPDATE SKIP LOCKED`
2. Processes each item atomically
3. Logs the result to `automation_runs` with status `completed` or `failed`
4. On failure: increments `retry_count`; items with `retry_count >= 3` are marked permanently failed

## Retry Policy

```
Attempt 1: immediate
Attempt 2: +2 seconds
Attempt 3: +4 seconds
After 3 failures: status = 'permanently_failed', alert emitted
```

Idempotency is enforced via:
```sql
INSERT INTO automation_runs (event_id, rule_id, status)
VALUES ($1, $2, 'running')
ON CONFLICT (event_id, rule_id) DO NOTHING;
```

## Accessing Worker Health

**Dashboard:** Worker health is displayed in the "Worker Status" panel on `/admin/runtime/workstreams`.

**API:** The `workers` field on `PlatformHealthReport` from `GET /api/admin/runtime/workstreams`.

## Incident Response

If `failureRate > 0.20` (critical):
1. Check `automation_runs` WHERE `status = 'failed'` in the last 30 minutes
2. Inspect `error_message` column for patterns
3. Verify Supabase Edge Function logs for the specific worker
4. Check if a dependency (supabase, redis) caused the failures
5. If systemic: pause the automation queue until the root cause is resolved
6. If isolated: manually retry specific failed runs or re-enqueue from the source event
