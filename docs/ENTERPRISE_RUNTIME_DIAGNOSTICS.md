# Enterprise Runtime Diagnostics

Generated by the VeloCity Workstream Reliability Framework (WRF) — Phase 8.

## Purpose

The diagnostics engine provides structured, machine-readable failure context for every workstream error. It eliminates generic "Something went wrong" messages in favor of actionable diagnostic payloads that operators can use to resolve issues without reading source code.

## Diagnostic Payload Format

Every captured diagnostic produces a `WorkstreamDiagnosticPayload`:

```typescript
interface WorkstreamDiagnosticPayload {
  workstream: string;
  correlationId: string;
  requestId: string;
  tenantId: string | null;
  franchiseId: string | null;
  organizationId: string | null;
  workflowId: string | null;
  stage: WorkstreamStage;
  status: WorkstreamStatus;
  latencyMs: number;
  retryCount: number;
  recoverable: boolean;
  timestamp: string;
  error?: WorkstreamError;
  dependencies?: DependencyHealthEntry[];
  attributes?: Record<string, string | number | boolean>;
}
```

## Capturing a Diagnostic

```typescript
import { captureWorkstreamDiagnostic } from "@/lib/workstream/diagnostics";

const payload = captureWorkstreamDiagnostic(state, {
  stage: "execute",
  error: wsError,
  attributes: { jobId, providerId },
});
```

## Span Tracing

Every workstream execution is wrapped with `withSpan()`, which:

1. Generates a W3C-compliant `traceparent` header via `startSpan()`
2. Records start time and stage name
3. On error: emits the error status and propagates
4. On success: records latency

```typescript
const result = await withSpan("dispatch", "execute", async () => {
  return await processDispatch(ctx);
}, context, { jobId: "job_123" });
```

## Root Cause Analysis

`buildRootCauseAnalysis(workstream, stage, error, dependency?)` returns a human-readable string with:

- Which workstream failed
- At which stage in the 14-stage lifecycle
- The underlying error message
- Which platform dependency was involved (if any)
- Suggested remediation steps

Example output:
```
[dispatch] Failure at stage load-dependencies
Dependency: supabase
Error: connection refused
Root cause: supabase is unreachable from the execute environment.
Suggested actions: Check Supabase project status at https://status.supabase.com.
  Verify NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY are set.
  Retry once connectivity is restored.
```

## Correlation IDs

Every workstream execution is assigned:
- `correlationId` — identifies the logical operation (stable across retries)
- `requestId` — identifies the individual attempt

Both are generated via `generateRequestId()` from `@/lib/tracing/span`. They are included in:
- Error display components (`WorkstreamErrorDisplay`)
- API error responses
- Admin dashboard links (`?correlation=<id>`)

## Accessing Diagnostics

Navigate to `/admin/runtime/workstreams?correlation=<correlationId>` to filter the admin dashboard to a specific execution. The `correlation` query param highlights the relevant row in the workstream matrix.

## Enterprise Error Standard

All errors surfaced to the UI must include:
- `title` — named error type (never "Unknown Error")
- `statusLabel` — human-readable status
- `code` — machine-readable error code (e.g., `AUTH_REQUIRED`, `DEP_UNAVAILABLE`)
- `httpStatus` — HTTP status code
- `dependency` — failing platform dependency (if applicable)
- `stage` — which of the 14 stages failed
- `retryable` — whether automatic retry is available
- `correlationId` — for support/incident tracking
- `suggestedActions` — at least one action operator can take
- `timestamp` — ISO 8601

Generic "Failed to load" messages are **forbidden** by the WRF enterprise error standard.
