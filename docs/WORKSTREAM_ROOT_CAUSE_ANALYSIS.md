# Workstream Root Cause Analysis

Generated by the VeloCity Workstream Reliability Framework (WRF) — Phase 8.

## Overview

Root cause analysis (RCA) is automatically generated for every workstream failure. The analysis is produced by `buildRootCauseAnalysis()` in `src/lib/workstream/diagnostics.ts` and surfaced in both the error display component and the admin diagnostics dashboard.

## RCA Generation Logic

The RCA function inspects:

1. **Workstream ID** — maps to the registry definition to understand dependencies and criticality
2. **Stage** — identifies where in the 14-stage lifecycle the failure occurred
3. **Error** — the thrown error, normalized to `WorkstreamError` via `toWorkstreamError()`
4. **Dependency** — the specific platform dependency that was involved (if any)

## Stage → Common Root Causes

| Stage | Common Causes | Typical Resolution |
|-------|--------------|-------------------|
| `initialize` | Missing env vars, code error | Check deployment config |
| `authenticate` | Expired session, JWT malformed | Re-authenticate |
| `resolve-tenant` | Missing tenant_id in JWT, deleted tenant | Check tenant existence in Supabase |
| `resolve-franchise` | Franchise deleted or tenant mismatch | Verify franchise record |
| `validate-membership` | Subscription expired, plan downgrade | Upgrade subscription |
| `validate-rbac` | Role changed, permission removed | Check role assignment |
| `load-dependencies` | Supabase down, Redis unreachable | Check platform status |
| `execute` | Business logic error, data constraint | Check error message; may need data fix |
| `persist` | DB write failed, RLS violation | Check RLS policies; check data |
| `publish-events` | Queue full, network partition | Check automation_queue table |
| `notify` | Twilio/SendGrid down, invalid contact | Check notification provider |
| `observe` | Telemetry write failed | Non-critical; retry automatically |
| `recover` | Recovery exhausted, circuit open | Manual intervention required |
| `certify` | Lifecycle assertion failed | Check workstream certification status |

## Dependency-Specific RCA

### supabase
- Check project health at https://status.supabase.com
- Verify `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- Check RLS policies haven't changed
- Check connection pool limits

### redis
- Verify Redis instance is running (check `REDIS_URL` env)
- Check if Redis is configured at all (`redis.isConfigured`)
- Check memory usage and eviction policy

### stripe
- Verify `STRIPE_SECRET_KEY` is set and not a test key in production
- Check Stripe status at https://status.stripe.com
- Verify webhook signing secret is valid

### anthropic
- Verify `ANTHROPIC_API_KEY` is set and valid
- Check rate limits; AI workstreams have built-in fallbacks
- Verify model ID is available in the account

### google-maps
- Verify `GOOGLE_MAPS_API_KEY` is set
- Check API quota usage in Google Cloud Console
- Ensure Maps JavaScript API and Geocoding API are enabled

## RCA in the UI

The `WorkstreamErrorDisplay` component surfaces the RCA as part of the enterprise error format. The `Open Diagnostics` action links to `/admin/runtime/workstreams?correlation=<correlationId>` for detailed investigation.

## RCA in the API

`GET /api/admin/runtime/workstreams` returns `errors[]` on the `PlatformHealthReport` object, each containing a root cause string generated by this engine.

## Incident Response Runbook

1. Note the `correlationId` from the error display
2. Navigate to `/admin/runtime/workstreams?correlation=<id>`
3. Identify the failing workstream and stage
4. Check the dependency health panel for the involved platform dependency
5. Follow the dependency-specific RCA guidance above
6. If the worker is in recovery, verify `automation_runs` for retry count
7. Once resolved, use the `Retry` action or wait for automatic retry
